========================================================
 CHROME LOCAL STORAGE (LevelDB) — FILE STRUCTURE EXPLAINED
========================================================

Local Storage/
└── leveldb/
    ├── 000003.log          Write-ahead log (recent writes not yet compacted)
    ├── 000005.ldb          Sorted table file (actual stored key-value data)
    ├── 000006.ldb          Another sorted table file
    ├── CURRENT             Points to the active MANIFEST file
    ├── LOCK                Lock file so only one process touches the DB
    ├── LOG                 Internal LevelDB operation log (debug info)
    ├── LOG.old             Previous session's LOG file
    └── MANIFEST-000004     Tracks which .ldb files are valid/current


--------------------------------------------------------
FILE-BY-FILE BREAKDOWN
--------------------------------------------------------

1) LOCK
--------
- Empty file, used purely for process-level locking.
- Chrome acquires a lock on this file when the DB is opened.
- Prevents two processes from writing to the same DB at once.
- This is why the DB can appear "locked" if inspected while
  Chrome is running.


2) 000003.log  (Write-Ahead Log / WAL)
----------------------------------------
- Every localStorage.setItem() call is appended here FIRST,
  sequentially (fast — no sorting needed).
- Also mirrored in memory as a "memtable."
- If Chrome crashes before the memtable is flushed to disk,
  this log is replayed on next startup to recover the writes.
- Once the memtable fills up, it is flushed to disk as a new
  .ldb file, and a fresh .log file is started.


3) 000005.ldb / 000006.ldb  (Sorted String Tables / SSTables)
----------------------------------------------------------------
- The actual persisted key-value data.
- Keys are stored in SORTED order → enables fast lookups and
  range scans via binary search + block index.
- LevelDB is a Log-Structured Merge-tree (LSM-tree):
    - Data is organized into "levels" (Level 0, 1, 2, ...)
    - Background "compaction" merges smaller/older .ldb files
      into fewer, larger, optimized ones.
    - Overwritten or deleted keys get dropped during compaction.
- This is where "LevelDB" gets its name (from these levels).


4) MANIFEST-000004
--------------------
- The database's "table of contents."
- Tracks which .ldb files currently exist, which level each
  belongs to, and the key ranges they cover.
- Every compaction or new file creation appends an entry here.


5) CURRENT
------------
- Tiny text file containing just the name of the active
  MANIFEST file (e.g., "MANIFEST-000004").
- Needed because old/stale MANIFEST files can exist during
  transitions — CURRENT tells LevelDB which one to trust.


6) LOG / LOG.old
------------------
- Plain-text, human-readable logs of internal LevelDB activity:
  compactions, file creations, errors, recovery events.
- Purely for debugging — NOT used to reconstruct actual data.
- LOG.old = previous session's log, rotated out on new startup.


--------------------------------------------------------
THE WRITE PATH (PUTTING IT TOGETHER)
--------------------------------------------------------

  setItem() call
        |
        v
  Appended to 000003.log (WAL) + written to in-memory memtable
        |
        v
  Memtable fills up
        |
        v
  Flushed to disk as a new .ldb file (e.g., 000005.ldb)
        |
        v
  MANIFEST updated to record the new file
        |
        v
  CURRENT still points to the correct MANIFEST
        |
        v
  Background compaction later merges/cleans up .ldb files


--------------------------------------------------------
NOTE
--------------------------------------------------------
This same engine (LevelDB, and its modern variants) also
powers IndexedDB and parts of Chrome's cache system — so this
file pattern shows up repeatedly under a Chrome profile
(see chrome://version → Profile Path).
